# Compared with alternatives

protoarray sits where three kinds of tools meet: JSON and the libraries that make it typed or
smaller (fast-json-stringify, superjson, devalue, JSONH, compress-json), the interface definition
languages built for schema evolution (Protocol Buffers through protobufjs, protobuf-es and
ts-proto, Avro, Thrift, the zero-copy FlatBuffers and Cap'n Proto, Bebop, typia's compiled codecs,
schemapack), and the schemaless binary formats (MessagePack through msgpackr and
@msgpack/msgpack, CBOR, BSON, Node's `v8.serialize`, Amazon Ion). The table below compares it with
twenty-two of them, every feature in one table, rather than a few convenient libraries in a few
convenient rows.

## What the table shows

- **Positional JSON is a small corner.** Eleven of the twenty-three travel over a JSON or text
  channel as they are, and protoarray is the only one of them that writes neither the names of the
  fields nor numbers in their place: the others write the names (or Thrift's field ids) in every
  object, or once per list (JSONH, compress-json) with no schema to check the values against. The
  formats that drop the names (tag numbers, positions, vtable slots) are binary, Thrift's JSON
  protocol aside, and need base64 on a channel that carries text.
- **Evolution past append-only is rare.** Every format with a schema lets you add fields.
  Reading an older writer's payload into the current reader's shape, with renames, defaults and
  widened types, is Avro's (`createResolver`) and protoarray's (`resolve`); Protocol Buffers and
  Thrift match tag numbers and skip what they do not know. Only avsc and protoarray compute a
  fingerprint of a schema, and only protoarray has a registry and an envelope built in; the
  Protocol Buffers libraries have `Any` and a third-party registry.
- **Decoding untrusted input differs more than the speed does.** Eleven of the twenty-three
  overflow the stack with a raw `RangeError` on deeply nested input, devalue at about 2,200
  levels and `v8.deserialize` at about 4,150. In five a `__proto__` key in the payload replaces
  the prototype of a decoded object (JSONH, compress-json, the maps of ts-proto and avsc, typia's
  protobuf records). FlatBuffers, Bebop and Ion's binary reader turn a truncated or corrupt
  buffer into garbage or `null` without an error. protoarray takes its keys from the schema,
  checks the wire by default and turns an overflow into a `DecodeError` with a path.
- **Encoding trusts the values almost everywhere.** fast-json-stringify, Thrift, FlatBuffers,
  Cap'n Proto and Bebop write a string given for an integer as `0`, or coerce it, without an
  error; protobufjs's `encode` coerces too and checks with a separate `verify`. protoarray trusts
  its values as well, which is the speed the benchmarks measure, and checking them is
  metaschema's `check` of the same definition, with a benchmark row for what it costs.
- **Code generation is a trade.** avsc and schemapack cannot run where `new Function` is
  forbidden (avsc cannot even be loaded), and protobufjs's reflection, msgpackr's and cbor-x's
  records compile code and fall back, or need static code. ts-proto, Thrift, FlatBuffers,
  Cap'n Proto and typia need a native compiler or a TypeScript transform in the build.
  protoarray reads its schemas at runtime, generates code where it may, falls back to closures,
  and writes standalone modules for the runtimes that allow no eval.
- **Columns and differences are protoarray's alone** in this set; the Protocol Buffers
  libraries, FlatBuffers and the record extensions of msgpackr and cbor-x save bytes other ways
  (packed scalars, shared strings, structures written once).
- **Some are no longer moving.** schemapack (last release 2016-08), JSONH (2017-07) and Amazon
  Ion's JavaScript implementation (2024-04).

protoarray's own gaps are in the table as such: JavaScript is its only implementation (the wire is
[specified](/guide/wire-format), nobody else reads it yet), it has no zero-copy reads, an absent
field and `null` are the same on the wire, and `parse` itself has no length limit (the stream
parsers do).

## How the table was made

- **From the code, not the README.** Each library was installed at its latest version from npm
  (October 2026) and every cell decided by reading its source, and where the behaviour was not
  obvious from reading (a `__proto__` key in a payload, 100,000 levels of nesting, a truncated
  buffer, a wrong type given to encode), by running a script against it. A README claim the code
  does not back is not counted, and the footnotes say where the two disagree.
- **Generated code without native compilers.** protoc plugins (protoc-gen-es, ts-proto) were run
  on a `CodeGeneratorRequest` built by hand and `pbjs` on a `.proto`; for Thrift, FlatBuffers,
  Bebop and typia the generated code was written in the shape their generators emit, read from
  the generators' source, and run against the real npm runtimes.
- **Built in or official.** A feature counts as ✅ when the package has it or an official
  package of the same project does (named in the cell); a third-party package is ⚠️ and named.
  A ❌ means it is not built in: most of them can be written by hand on top.
- **The same questions for everyone.** The rows were fixed before any column was filled, and a
  row that does not apply to a kind of tool (a schema question for a schemaless format) is
  marked — rather than ❌.

The speed of the libraries that can be benchmarked side by side, their cold start and their
bundle sizes are on the [Benchmarks](/guide/benchmarks) page, with the method; this page is about
what each one does.
