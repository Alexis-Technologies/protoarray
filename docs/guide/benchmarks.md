# Benchmarks

Every number on this page comes from scripts in the repository, recorded in
[`bench/results/`](https://github.com/Alexis-Technologies/protoarray/tree/main/bench/results) and
[`bench/baseline.json`](https://github.com/Alexis-Technologies/protoarray/blob/main/bench/baseline.json),
and turned into these charts and tables by `pnpm bench:report`. They were measured on one machine,
named under each chart. Read them as relative guidance: the order and the ratios carry over to
other hardware, the exact figures do not.

## Compared with other libraries

`pnpm bench:compare` runs seven payloads through protoarray, JSON and eleven JavaScript codecs:
the Protocol Buffers of [protobufjs](https://github.com/protobufjs/protobuf.js) and
[protobuf-es](https://github.com/bufbuild/protobuf-es), the Avro of
[avsc](https://github.com/mtth/avsc), the MessagePack of [msgpackr](https://github.com/kriszyp/msgpackr)
and [@msgpack/msgpack](https://github.com/msgpack/msgpack-javascript), the CBOR of
[cbor-x](https://github.com/kriszyp/cbor-x), MongoDB's [BSON](https://github.com/mongodb/js-bson),
Node's `v8.serialize`, the typed JSON of [superjson](https://github.com/blitz-js/superjson)
and [devalue](https://github.com/sveltejs/devalue), and Fastify's
[fast-json-stringify](https://github.com/fastify/fast-json-stringify). Each library is used the
way its documentation shows
([`bench/compare/adapters.js`](https://github.com/Alexis-Technologies/protoarray/blob/main/bench/compare/adapters.js)):
the schema libraries get a schema of the same shape, a union is a protobuf `oneof`, an Avro union
of records and protoarray's discriminated union. Every (library, scenario) pair runs in a fresh
process, and an adapter has to give the scenario's value back through its own format before it is
timed.

Speed is end to end: an object to text or bytes, and the text or bytes back to an object. A round
trip is one of each. Pick a scenario and a metric; hover over or focus a bar for the time of one
call, the ratio to JSON, the spread of the rounds and the exact version.

### Reading the numbers

- **Records, strings and tagged messages** are where JSON transports live, and where protoarray
  is the fastest encoder of the comparison: `JSON.stringify` is native, the generated code that
  turns an object into its array adds tens of nanoseconds, and the array is about half the text.
  The binary codecs written in JavaScript encode strings byte by byte and fall behind.
- **Decoding**, protoarray is faster than JSON on every payload and faster than every codec on
  long strings, where `JSON.parse` reads UTF-8 natively and the binary codecs decode it in
  JavaScript. msgpackr with shared structures (a structure id and the values, the binary
  equivalent of protoarray) decodes the other payloads faster than `JSON.parse` can read text,
  and avsc, cbor-x's records and protobufjs are ahead on some shapes (lists of records, enums and
  booleans). Over a round trip protoarray is first on one record, long strings and tagged
  messages, second behind msgpackr on lists and sparse records and behind protobufjs on typed
  ones.
- **Numbers** are the honest exception: a double prints as up to 17 characters and parses back
  through a decimal conversion, where avsc and protobufjs read 8 bytes. Use a binary codec for
  dense numeric payloads.
- **Validation.** The wire is checked on decode and the values given to encode are trusted, so
  protoarray encodes the way protobufjs and msgpackr do, without checks, and decodes with them.
  Checking the values is metaschema's: the `codegen + metaschema check` row runs metaschema's
  `check` of the same schema before every encode, which is what validating each outgoing value
  costs.
- **Without eval.** The `closures` row is the backend protoarray falls back to where `new Function`
  is not allowed, at about the speed of JSON. The `standalone module` row is the same codec
  written into a module at build time (see [Standalone Modules](/guide/standalone)): what a strict
  CSP or an edge runtime gets instead, at the speed of generated code.
- **Sizes**: protoarray's wire is JSON text; the binary formats' bytes are before any base64 a
  text channel would add. After gzip or brotli the formats are close, and the `columns` layout is
  the smallest on lists. With the ids written as differences and the cities and tags interned
  (`columns, delta + intern`), the thousand records are another 17% smaller before compression
  and the smallest after it of any format here; interning the unique strings (names, emails)
  instead would make the gzip larger, since their table compresses worse than the strings in
  place.
- **The typed JSON libraries** (superjson, devalue) and v8.serialize need no schema: they write
  the keys and the type of every value, which is what they are for, and pay for it in speed and
  bytes. fast-json-stringify compiles a JSON Schema into a serializer and is the fastest encoder
  on sparse and typed records; it decodes with `JSON.parse` and writes the keys.

## Cold start

A schema is built once, so the tables above leave it out. A program that starts often (a CLI, a
serverless function, a page) pays for loading the library, building its schemas and the first
call, which runs before the engine has optimized anything. Each library runs ten times in a fresh
process, loading itself, building the schema of one record, encoding it and decoding it once.

## protoarray on its two backends

`pnpm bench` is the engine harness for protoarray alone: both backends and every layout, against
`JSON.stringify` and `JSON.parse` of the keyed object, with `--save` and `--compare` to track a
change on one machine. The generated code is ahead of JSON on most shapes, ×1.2 to ×2.2. It is
behind on a record of 70 flags, which travels as bitmask words JSON does not have to compute, on
decoding bytes, where the base64 has to be canonical, and level with it on encoding a sparse
record of 70 fields. The closures stay near JSON on most shapes and behind generated code by the
cost of one keyed store per present field, ×1.6 to ×1.9 on decode: `pnpm bench:sweep` prints that
cost from 4 to 256 fields, each backend in a fresh process (about 60 ns a field against 30, with
no step at 128 fields; see [Runtimes and CSP](/guide/runtimes#what-the-fallback-costs)).

## Running them

```bash
pnpm bench:compare --save        # the comparison and the cold start, bench/results/compare.json
pnpm size:compare --save         # bundle sizes, bench/results/size.json
pnpm bench:releases --ref v1.0.0 # a release (a tag), merged into bench/results/releases.json
pnpm bench:releases              # the current tree
pnpm bench --save                # the engine harness, bench/baseline.json
pnpm bench:report                # the charts and tables of this page and the README
```

Every run is manual and none is part of CI. Run them on an otherwise idle machine: a 5% difference
hides in the noise of a busy one. `--scenarios` and `--adapters` narrow `bench:compare`, and a
saved run merges into the results, so one library or scenario can be measured again on its own.
